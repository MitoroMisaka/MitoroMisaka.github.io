# Product Requirements Document: 个人技术博客网站（MitoroMisaka.github.io 重建）

> 日期: 2026-05-26
> 状态: 草案

## 目标

- 完全替换现有 `MitoroMisaka.github.io` 的裸 Jekyll 站点，重建为一个内容优先、长期可维护的个人技术博客。
- 建立统一的个人品牌首页，清晰展示作者身份、技术方向、代表项目与最新文章。
- 提供优秀的技术文章阅读体验，包括目录、阅读进度、代码块复制、主题切换、搜索、RSS 和评论。
- 形成稳定的写作与发布工作流，使新增文章、维护内容、迁移旧文都足够顺手。
- 在第一期以内聚的静态方案上线可用版本，为第二期的时间线、碎念、动态互动功能预留扩展空间。

## 用户故事

- 作为站点作者，我想用 MDX/Markdown 低摩擦地发布技术文章，以便持续沉淀 AI 工作流、开发实践和项目记录。
- 作为站点作者，我想有一个足够有辨识度的首页，以便别人一眼知道我是谁、我做什么、我最近在写什么。
- 作为首次访问的读者，我想快速理解站点定位并看到最近值得读的文章，以便决定是否继续浏览或订阅。
- 作为技术文章读者，我想获得清晰的目录、代码高亮、复制按钮、阅读进度和舒适的排版，以便高效阅读长文。
- 作为回访读者，我想按标签、分类或搜索找到旧文，并通过评论与作者互动。
- 作为移动端用户，我想在手机上也能顺畅浏览首页和文章页，不因为复杂布局而影响阅读。

## 功能范围

### In Scope

- 全新站点架构，完全替换旧 Jekyll 站点，而非在原结构上渐进改造。
- 基于静态优先方案的个人博客站点。
- 首页 Hero 区，包括：站点名、作者定位、一句话简介、社交入口、个人品牌氛围。
- 首页内容模块，包括：Recent Writing、基础项目展示、可选的简短碎念预览。
- 文章内容系统：支持 Markdown/MDX、frontmatter 元数据、分类、标签、草稿控制。
- 文章列表页与文章详情页。
- 技术文章阅读增强：目录（TOC）、阅读进度、代码高亮、代码复制、标题锚点、阅读时间。
- 全站主题切换：Light / Dark / System。
- 全站搜索（静态搜索方案）。
- 评论系统：使用 Giscus 接入 GitHub Discussions。
- 基础 SEO 能力：meta、OpenGraph、Twitter Card、sitemap、RSS。
- 基础信息页：About、Projects、Links 或等价的站点信息入口。
- 旧站已有文章或内容的迁移与重组织（仅迁有价值内容）。
- 保留或兼容重要旧 URL；无法原样保留时提供合理 redirect 方案。
- 响应式适配，覆盖桌面端和移动端。

### Out of Scope（这个版本不做）

- 自建 CMS 后台。
- 自建评论、登录、点赞、收藏、订阅系统。
- 复杂的多语言系统。
- 照片廊、完整时间线、完整碎念系统的正式版。
- 需要数据库支撑的动态统计面板。
- Newsletter 邮件投递系统。
- 过重的动画、粒子背景、3D 展示或强交互视觉实验。
- 在旧 Jekyll 工程上继续做兼容性修补。

## 技术约束

- 必须完全替换现有 `MitoroMisaka.github.io` 站点实现，不在旧 Jekyll 代码结构上继续演进。
- 第一阶段必须采用静态优先架构，优先保证内容发布与阅读体验，而不是先做后端能力。
- 部署目标为 Cloudflare Pages，站点应适配其静态构建与发布方式。
- 需要明确域名策略：`*.github.io` 为 GitHub 控制域名，不能直接由 Cloudflare Pages 托管；若暂无自定义域名，则第一期默认使用 Cloudflare Pages 提供的域名，或后续单独调整部署策略。
- 评论系统必须优先采用第三方托管集成方案（Giscus），避免第一期引入自建后端。
- 内容源必须为文件驱动，支持 Git 管理和本地编辑，不依赖线上编辑器。
- 设计风格必须参考 `https://innei.in` 的高留白、日系极简、内容优先气质。五期已基于 [Yohaku (余白)](https://github.com/Innei/Yohaku) 设计系统实现完整 Design Token 迁移（MIT 协议），暖纸白底 + 柔和珊瑚 accent + 10 级中性色阶 + 12 级字号系统。不能直接复制 Shiro 源码（AGPLv3）。
- 站点应保留未来扩展到 Cloudflare Workers / D1 / KV 的可能性，但第一期不以这些能力为前提。
- 必须兼顾桌面与移动端可用性，不能只针对桌面视觉设计。
- 新增内容流程必须足够简单，避免作者每次发文都需要手改复杂模板或重复配置。

## 质量标准

- 性能基准:
  - 首页与文章页的 Lighthouse Performance 分数目标 >= 90（桌面端）。
  - Accessibility 分数目标 >= 95。
  - 首屏内容应尽可能静态输出，避免阻塞渲染的重客户端脚本。
- 可维护性要求:
  - 内容、布局、组件、样式职责清晰分离。
  - 文章元数据结构稳定、可校验。
  - 常用页面和组件可复用，避免首页/文章页逻辑散落。
  - 站点信息、导航、社交链接、SEO 配置可集中维护。
- 内容维护要求:
  - 新文章创建路径明确，frontmatter 规范统一。
  - 旧文迁移后能在新系统中一致渲染。
  - 分类、标签、slug 规则稳定，不频繁变化。
- 测试覆盖标准:
  - 至少具备构建成功校验。
  - 至少覆盖核心页面的手动验收：首页、文章列表、文章详情、搜索、主题切换、评论入口。
  - 至少验证 RSS、sitemap、主要 SEO 元标签和移动端基础可用性。

## UI/UX 参考

- 参考项目 A: `https://innei.in`
  - 重点参考：首页 Hero 的个人品牌表达、Recent Writing 模块、极简导航、高留白布局。
  - 重点参考：文章页的标题区、元信息、右侧目录、阅读进度、提示块、代码块体验。
- 参考项目 B: 当前 `https://mitoromisaka.github.io`
  - 保留其已有的站点名称、作者定位、AI 工作流与技术写作方向，但整体体验需全面升级。
- 风格倾向:
  - 日系极简
  - 柔和低饱和配色
  - 内容优先
  - 轻卡片化
  - 长文阅读友好
  - 强调个人品牌而非营销感

## 版本边界

### 第一期开站标准

- 首页、文章系统、搜索、评论、RSS、SEO、主题切换全部可用。
- 至少迁移并发布一批核心文章，能够体现站点定位。
- 视觉风格与旧站拉开明显差异，达到“新站”而不是“旧站换皮”的程度。
- Cloudflare Pages 线上部署完成，可公开访问。

### 第二期扩展方向

- Timeline / 时光页
- 正式的 Notes / 碎念系统
- Projects 页增强
- 自定义互动（如点赞/reaction）
- Newsletter
- 站点数据统计与更多 Cloudflare 动态能力

## 成功标准

- 用户进入首页后，能在数秒内理解“这是谁的站、主要写什么、最近有什么值得读”。
- 作者能够稳定地把新的技术文章发布到站点，而不再受旧 Jekyll 结构限制。
- 文章页在代码阅读、长文导航和评论互动方面明显优于旧站。
- 站点视觉气质成功靠近目标参考，但依然保有 `MitoroMisaka` 的个人辨识度。
